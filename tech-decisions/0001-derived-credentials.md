# ADR-0001: 定义不写 id，凭证按「工作区 id + 名字」派生

状态：已接受
日期：2026-09-19

## 背景

工作流与步骤需要稳定的标识符：工单封面以 `workflow_id` 引用所引工作流，工作记录以 `step_id` 指认步骤，领域事件以二者去重，跨端对账以二者为主键。

v1 将凭证显式写入定义文件，由人工编制 UUID。该做法存在三个问题：

1. 凭证本身无语义，编制是纯维护负担；定义格式迁移时须批量补编，实验室 v1 至 v2 的迁移即以编造凭证为第一道工序。
2. 编制过程缺乏一致性约束：定义被复制后，副本与原件可携带同一凭证，形成两个事实共享一个身份。
3. 凭证落盘并纳入版本控制后，每次重新生成都会引入与内容无关的 diff。

## 术语

**凭证**：工作流、步骤、工单、工作记录的标识符。

**派生**：以确定性函数从既有事实计算凭证；同一输入在任意时刻、任意平台计算结果一致。

**uuid5**：RFC 4122 定义的第五版 UUID，输入为命名空间与名称，基于 SHA-1 计算；输出恒定，且符合 UUID 语法。

## 选项

选项一，显式编号：凭证写入定义文件。优点是凭证与内容解耦，改名不换凭证，且可随时重新生成；缺点是编制与维护均为人工负担，复制场景下无重号约束，落盘引入与内容无关的 diff。

选项二，按定义内容哈希：以定义全文的哈希值作凭证。优点是全自动；缺点是内容任一字节变化（包括勘误）即改变凭证，在途工单的引用随之失效。凭证不稳定，不满足对账要求。

选项三，按「工作区 id + 名字」派生：定义文件不含身份字段，凭证读取时现算。优点是新增与迁移零编制成本，凭证可由任意一方独立重算，作用域化保证跨工作区同名不冲突；缺点是改名即换凭证，同一作用域内同名实体不可并存。

选择选项三。

## 决定

### 凭证算法

采用 uuid5。uuid4 随机生成，多端无法独立重现同一凭证，派生的前提不成立；自定哈希截断则须自行定义输出格式与碰撞处理，uuid5 是 RFC 4122 的现成规范。

### 派生输入

工作流凭证 = `uuid5(命名空间, "<工作区 id>/<工作流名>")`；步骤凭证 = `uuid5(命名空间, "<工作流凭证>/<步骤名>")`。

输入包含工作区 id，因为名字的作用域是单个工作区而非全局；不含工作区 id 会使两个工作区的同名工作流得到同一凭证，账目随之串号。步骤以工作流凭证为前缀分层派生，使凭证的层级与定义的结构层级同形：步骤名只须在工作流内唯一，且由步骤凭证可独立验证其所属工作流。拼接符 `/` 消除输入分段歧义。

### 计算时机

凭证在读取时现算，不持久化。持久化会使本方案退化回显式编号，重新引入落盘、diff 与复制重号问题；现算保证凭证始终是可重算验证的推论，定义文件只承载内容，不承载身份。

### 命名空间

命名空间为钉死的常量，定义于 `apps/qtcloud-work/src/cli/src/ids.rs` 的 `NAMESPACE`。命名空间的取值决定全套凭证的值域，变更命名空间将使全部已落盘引用（工单封面、领域事件）失效，因此命名空间属于接口契约，其变更必须另立 ADR。

### 工单与工作记录的凭证

由程序在创建时生成 uuid4，落笔后不可变。二者是一次性事实，不存在按名字重算的需求，派生无收益；采用随机生成亦避免与派生凭证共用名字这一输入。

### 引用与查填

工单封面所引 `workflow_id` 在开单时查填，落笔即封；定义此后改名不回填封面，核对时以开单时的工作流名重算比对。流水中的 `step_id` 由账本按 `step` 名查填，人工不写。

### schema 约束

定义文件的 schema 校验拒绝 `id` 字段，防止显式编号与派生两套身份来源并存。

## 影响

- 定义文件不含身份字段：新增与迁移零编制成本，存量定义零改动读入。
- 改名即换凭证，是唯一的身份变更通道；改名前须确认没有在途工单以旧名派生的凭证引用该工作流。
- 同一工作区内工作流同名并存不被支持，由 `workflow create` 的重名检查与装载时的名字一致性核对兜住。
- 各平台（cli、studio）须实现同一 uuid5 算法并引用同一命名空间常量，跨端一致性由对账测试验证。
- 步骤名在同一工作流内须唯一，这是步骤凭证稳定性的前提；现行校验未显式覆盖重复步骤名，列入补齐项。
