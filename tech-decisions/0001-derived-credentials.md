# ADR-0001: 定义不写 id，凭证按「工作区 id + 名字」派生

状态：已接受
日期：2026-09-19

## 背景

工作流与步骤需要一个身份编号：工单封面引用它（`workflow_id`）、工作记录凭它指认步骤（`step_id`）、领域事件靠它去重、跨端对账认它。编号从哪来，决定写定义的成本与账的稳定性。

v1 把编号写进定义文件，人手编 UUID。实际后果：

- 写定义的成本集中在编无含义的号上；实验室把 v1 定义迁成新格式时，第一件事就是批量编造；
- 手编的号没有任何一致性约束——复制一份定义改个名，两份文件可以带同一枚号；
- 编号落盘即入 git，重生成一次就是一次无谓的 diff。

## 选项

1. **显式编号（v1 现状）**：定义里写 `id`，人编或工具生成后落盘。
   优：编号与内容解耦，改名不换号；想换号随时重生成。
   劣：编号是纯维护负担；复制与迁移场景下重号、漏号无约束。

2. **按内容哈希**：拿定义全文算哈希作编号。
   优：全自动，不用人碰。
   劣：改一个字（哪怕错别字）编号就变，在途工单的引用随之悬空；编号不稳定，对账失去基础。

3. **按「工作区 id + 名字」派生**：定义不写编号，读取时用 uuid5 现算，命名空间常量钉死。
   优：写定义只剩起名（名字本来就要起）；同样输入永远同样输出——可重放、可对账、各平台各算一致；跨工作区同名各得各号，账不串。
   劣：换编号只能改名或挪工作区；同一工作区「同名并存」不成立。

## 决定

- 工作流与步骤的**定义不写 `id`**。读取时现算：工作流凭证 = `uuid5(命名空间, 工作区 id + 工作流名)`；步骤凭证 = `uuid5(命名空间, 工作流凭证 + 步骤名)`。命名空间是一枚钉死的常量，属契约，变更须另立 ADR。
- **工单与工作记录的编号由程序发**（随机 UUID），开单、记账时生成，落笔后不变——它们是一次性事实，不需要「按名字重算」的性质。
- 工单封面所引 `workflow_id` **开单时查填、落笔即封**；此后定义改名不回填封面，核对以开单时的名字重算。
- 流水里的 `step_id` 由账本按 `step` 名查填，人不写。

## 影响

- 定义文件瘦身；新增与迁移不再手编编号，存量定义零改动读入。
- **改名即换身份**：改名前须确认没有在途工单以旧名所派的编号引用它；这是本方案唯一的身份变更通道。
- 同一工作区同名并存不被支持，由 `workflow create` 的重名检查与装载时的名字一致性核对兜住。
- 各平台（cli 的 Rust、studio 的 Dart）必须实现同一 uuid5 算法与同一命名空间；对账测试钉住「两侧算得一致」。
- 校验只认写下的字段：定义文件里出现 `id` 一律拒绝，防止两套身份来源并存。
