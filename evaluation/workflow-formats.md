# 评估：招聘流程在两种工作流格式下的表达

基线 `bd70d08`（gallery 新增 recruitment-flow）、`da98bbc`（实验室 recruitment.yaml）。两份正本：本仓 gallery 的 `workflows/recruitment-flow.yaml`，与 `adapters/quanttide-feishu/examples/quanttide-feishu-lab/flows/recruitment.yaml`。材料来源：`qtrecurit-private/docs/handbook/workflow.md`（2026-08 按实际运行更新）。评估日 2026-10-10。

同一件事——飞书上的招聘流程——按两处的规范各写了一份。这份评估记三件事：两份各是什么、结构上哪里同哪里不同、以及拿这条真实流程当试金石，试出领域侧工作流格式的哪些缺口。第四节记我先前判错又改正的两条。

## 一、两份各是什么

| | 领域侧（gallery） | 适配层（实验室） |
| :-- | :-- | :-- |
| 文件 | `workflows/recruitment-flow.yaml` + 同名 `.md` | `flows/recruitment.yaml` |
| 组织单位 | 步骤，九步，一步一节 | 状态十一、迁移九 |
| 每步写什么 | 输入、过程、输出、验收 | 触发、执行者、副作用 |
| 执行者词汇 | `agent` / `human`；判据分 `rule` / `agent` / `human` | 人 / 系统 / 半自动 |
| 验收 | 三层，每步都带 | 无，只有副作用 |
| 触发的表达 | 隐含（上一步做完） | 显式（什么事件让迁移发生） |
| 跑法 | 写在描述里：`qtcloud-work task --new … --workflow …` | 未写 |
| 主轴 | 产物的流动 | 对象的状态 |

两份材料同源，都从 `workflow.md` 取实况，未编造：文件夹漂移与 Spam 误判这两处卡点，领域侧落在 `fetch-drifted` 与 `spam` 两步，适配层落在收集范围与迁移上。

## 二、结构上的异同

**同**：都是「流程即数据」——YAML 不把流程写死在代码里；都标执行者；都出自同一份实况。

**异**，四条：

1. **主轴不同。** 领域侧以产物的流动为主轴：手上先有哪份东西，再做哪份，是流水线。适配层以对象的状态为主轴：一个候选人此刻在哪一格、什么事件推它走，是状态机。同一件事，一个问「该做什么了」，一个问「它走到哪了」。
2. **验收的有无。** 领域侧每步带三层验收（`rule` 程序当场核、`agent` 智能体照判准审、`human` 留给人拍板），这是它最硬的资产；适配层那份只有副作用，没有任何验收。同一件事两边一比，验收该归哪层就落定了：**验收归领域侧**。
3. **触发在哪。** 适配层有显式的触发（邮件到达、表里出现一条记录）；领域侧的触发是隐含的（上一步做完）。领域侧没有位置安放事件。
4. **词汇的粗细。** 领域侧的执行者是 `agent` / `human`，判据另有 `rule`；适配层我写成了人 / 系统 / 半自动。后者的「系统」在前者里没有对应的词——程序能执行的两种东西（规则引擎当场核、智能体照判准审）被含糊地并成了一个。

## 三、试出来的缺口

拿招聘这条流程试，领域侧的格式有四处装不下或说不清。每条给现象、依据与后果。

### 缺口一：流程只有直线

`steps` 是有序列表，一步接一步。招聘里却有三样东西装不下：**回流**（问卷没交 → 无响应 → 后来交了）、**分叉**（淘汰 / 不推荐 / 推荐池 / 留用四路并存）、**并行**（几十个候选人同时在各步上）。现有九个案例全是直线管道——格式是为直线设计的，遇到有环的流程只能硬塞或拆成多条。

### 缺口二：时间不是一等公民

判据三类（`rule` / `agent` / `human`）说的是「谁判」，没有说「等多久」。而招聘里最容易堵的一步恰恰由时间定义：问卷发出去 N 天没回音就该有人管。「等 N 天」现在只能塞进一条 `rule` 命令里，等待与超时不是格式的语义。

### 缺口三：被服务的对象没有身份

ADR-0001 给工作流、步骤、工单、工作记录都造了号，锚定终身不变。唯独没有给**它服务的对象**造号。招聘里「这个人」是贯穿始终的对象：他投递、交问卷、进群、被评估、被推荐，中间可能经过多趟行程（多张工单）。跨行程把同一个人归一，现在没有答案——每张工单认得自己那次行程，没人认得这个人。

### 缺口四：与适配层缺一层缝合

领域侧有验收没触发，适配层有触发没验收。「什么事件发生 → 做哪一步 → 怎么算过」这句完整的话，两边都说不全。这不是谁漏了东西，是**两层之间那道缝还没有定义**：事件由适配层看见、步骤由领域侧定义、验收由领域侧持有，但「看见的事件怎么落到那一步上」没有归属。

## 四、先前判错、已改正的两条

1. **~~「工作区被默认在本仓」~~**——错。CLI 评估写明「四处位置都有缺省，也可由启动参数装载；位置不进模型」。跨仓的工作流本来就支持，是我没读到这里。
2. **~~「没有东西现在在哪」~~**——错。工单是一次行程、内页是只增不改的流水，账本记每一步过没过；「东西现在在哪」由工单与账本承载，且支持多趟行程。我把适配层那份状态机当成了唯一的状态表达。

## 五、处置建议

1. **缺口二（时间）最便宜**：给判据加一类「到时」语义（或允许步骤声明等待与超时），不必动主线。
2. **缺口一（分支与回流）中等**：要支持就得先在规格里定清分支与汇合怎么表达，动的是格式正本，不是某个案例。
3. **缺口三（对象身份）最重**：这是一条 ADR 级别的判断——给对象也造号（沿用 uuid5 那套），还是把对象身份交给适配层持有、领域侧只认行程。两种都自洽，混着来会串号。
4. **缺口四（缝合）与上面三条互斥选择**：「触发」字段是加在领域侧还是加在适配层，二选一，别两边都加——两边都加就是两个事实源。
